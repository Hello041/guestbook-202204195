# 미니 방명록 스펙

Status: ready-for-agent

용어는 `GLOSSARY.md`를 따른다 (방명록 글 = Entry, 메시지 = Message, 작성자 이름 = Author name, 비밀번호 = Password, 작성 시각 = Created time, 수정됨 = Edited). 권한 모델은 ADR-0001(계정 없음, 글마다의 비밀번호가 유일한 권한 수단)을 따른다.

## Problem Statement

방문자가 회원가입이나 로그인 없이 가볍게 이름과 한마디를 남기고, 다른 사람들이 남긴 글을 최신순으로 볼 수 있는 공간이 필요하다. 동시에 글쓴이는 자신이 쓴 글을 나중에 고치거나 지울 수 있어야 하지만, 다른 사람이 남의 글을 고치거나 지워서는 안 된다. 계정이 없으므로 "이 글이 내 것"임을 증명할 수단이 따로 필요하다.

## Solution

한 페이지짜리 미니 방명록을 만든다. 방문자는 작성자 이름, 메시지, 비밀번호를 입력해 방명록 글을 남긴다. 페이지에는 모든 글이 작성 시각 기준 최신순으로 나열되며, 각 글에는 작성자 이름, 메시지, 작성 시각, (수정된 경우) "(수정됨)" 표시가 보인다. 글마다 [수정]/[삭제] 버튼이 있고, 누르면 그 글 아래에 인라인 폼이 열려 비밀번호를 입력하게 한다. 비밀번호가 맞으면 메시지가 수정되거나 글이 삭제되고, 틀리면 거부되며 폼 안에 "비밀번호가 일치하지 않습니다."가 표시된다. 헤더에는 제목과 함께 `개발자: 김정효 (202204195)`가 항상 표시된다.

## User Stories

### 작성 (Create)

1. 방문자로서, 작성자 이름·메시지·비밀번호를 입력해 방명록 글을 남기고 싶다. 그래야 로그인 없이 흔적을 남길 수 있다.
2. 방문자로서, 회원가입이나 로그인 없이 바로 글을 쓰고 싶다. 그래야 부담 없이 참여할 수 있다.
3. 방문자로서, 글을 제출하면 내 글이 목록 맨 위에 바로 나타나길 원한다. 그래야 글이 잘 등록됐음을 알 수 있다.
4. 방문자로서, 제출에 성공하면 입력 폼이 비워지길 원한다. 그래야 실수로 같은 글을 두 번 올리지 않는다.
5. 방문자로서, 이름·메시지·비밀번호 중 하나라도 비어 있으면 제출이 거부되고 이유가 안내되길 원한다. 그래야 무엇을 고쳐야 하는지 안다.
6. 방문자로서, 공백만 입력한 값은 빈 값으로 취급되길 원한다. 그래야 내용 없는 글이 등록되지 않는다.
7. 방문자로서, 이름이 20자를 넘으면 거부되고 안내받고 싶다. 그래야 목록이 깔끔하게 유지된다.
8. 방문자로서, 메시지가 500자를 넘으면 거부되고 안내받고 싶다. 그래야 짧은 방명록 성격이 유지된다.
9. 방문자로서, 비밀번호가 4자 미만이거나 20자를 넘으면 거부되고 안내받고 싶다. 그래야 너무 쉬운 비밀번호를 쓰지 않는다.
10. 방문자로서, 입력 오류로 제출이 거부돼도 내가 쓴 내용이 지워지지 않길 원한다. 그래야 처음부터 다시 쓰지 않아도 된다.
11. 방문자로서, 다른 사람과 같은 이름으로 글을 쓸 수 있길 원한다. 이름은 신원이 아니라 표시용 라벨이기 때문이다.
12. 방문자로서, 비밀번호 입력칸이 가려진 채로 표시되길 원한다. 그래야 옆 사람이 내 비밀번호를 보지 못한다.

### 조회 (Read)

13. 방문자로서, 누구나 전체 방명록 글 목록을 볼 수 있길 원한다. 그래야 다른 사람들이 남긴 글을 읽을 수 있다.
14. 방문자로서, 목록이 작성 시각 기준 최신순으로 정렬되길 원한다. 그래야 새 글을 먼저 볼 수 있다.
15. 방문자로서, 각 글의 작성자 이름, 메시지, 작성 시각을 보고 싶다. 그래야 누가 언제 무엇을 남겼는지 안다.
16. 방문자로서, 작성 시각이 한국 시간 기준 `YYYY-MM-DD HH:mm` 형식으로 보이길 원한다. 그래야 헷갈리지 않는다.
17. 방문자로서, 메시지가 수정된 글에는 "(수정됨)" 표시가 보이길 원한다. 그래야 원래 내용이 바뀌었다는 걸 안다.
18. 방문자로서, 글이 수정돼도 목록에서의 위치가 바뀌지 않길 원한다. 그래야 정렬이 최초 작성 순서를 계속 반영한다.
19. 방문자로서, 페이지를 넘기지 않고 모든 글을 한 번에 보고 싶다. 그래야 전체 목록을 쉽게 훑어볼 수 있다.
20. 방문자로서, 아직 글이 없으면 "아직 작성된 글이 없습니다. 첫 글을 남겨보세요!"라는 안내를 보고 싶다. 그래야 빈 화면이 고장난 것처럼 보이지 않는다.
21. 방문자로서, 메시지의 줄바꿈이 목록에서도 유지되길 원한다. 그래야 쓴 모양 그대로 읽힌다.
22. 방문자로서, 다른 사람이 쓴 메시지에 들어 있는 HTML이나 스크립트가 실행되지 않고 글자로만 보이길 원한다. 그래야 방명록이 안전하다.
23. 방문자로서, 어떤 방식으로도 다른 사람의 비밀번호(또는 그 해시)를 볼 수 없길 원한다. 그래야 내 글의 권한이 보호된다.

### 수정 (Update)

24. 글쓴이로서, 내 글의 [수정] 버튼을 누르면 그 글 아래에 인라인 수정 폼이 열리길 원한다. 그래야 어떤 글을 고치는지 헷갈리지 않는다.
25. 글쓴이로서, 수정 폼에 현재 메시지가 미리 채워져 있길 원한다. 그래야 일부만 고칠 수 있다.
26. 글쓴이로서, 비밀번호를 입력해 내 글의 메시지를 수정하고 싶다. 그래야 오타나 내용을 바로잡을 수 있다.
27. 글쓴이로서, 메시지만 수정할 수 있고 작성자 이름과 작성 시각은 바뀌지 않길 원한다. 그래야 글의 정체성이 유지된다.
28. 글쓴이로서, 비밀번호가 틀리면 수정이 거부되고 폼 안에 "비밀번호가 일치하지 않습니다."가 표시되길 원한다. 그래야 왜 안 됐는지 안다.
29. 글쓴이로서, 비밀번호가 틀려 거부돼도 내가 고쳐 쓴 메시지가 폼에 그대로 남아 있길 원한다. 그래야 비밀번호만 다시 입력하면 된다.
30. 글쓴이로서, 수정한 메시지도 작성할 때와 같은 규칙(공백 제거 후 1~500자)으로 검사받길 원한다. 그래야 수정으로 빈 글이 생기지 않는다.
31. 글쓴이로서, 수정에 성공하면 폼이 닫히고 바뀐 메시지와 "(수정됨)"이 바로 보이길 원한다. 그래야 성공했음을 알 수 있다.
32. 글쓴이로서, 수정 폼을 취소하고 닫을 수 있길 원한다. 그래야 마음이 바뀌었을 때 아무것도 바뀌지 않는다.
33. 방문자로서, 남의 글 비밀번호를 모르면 그 글을 수정할 수 없길 원한다. 그래야 내 글도 남에게 수정되지 않는다.
34. 글쓴이로서, 수정하려는 글이 그 사이 삭제됐다면 그 사실을 안내받고 싶다. 그래야 없는 글을 붙잡고 헤매지 않는다.

### 삭제 (Delete)

35. 글쓴이로서, 내 글의 [삭제] 버튼을 누르면 그 글 아래에 비밀번호 입력 폼이 열리길 원한다. 그래야 실수 클릭만으로 글이 지워지지 않는다.
36. 글쓴이로서, 비밀번호를 입력해 내 글을 삭제하고 싶다. 그래야 더 이상 남기고 싶지 않은 글을 지울 수 있다.
37. 글쓴이로서, 비밀번호가 틀리면 삭제가 거부되고 폼 안에 "비밀번호가 일치하지 않습니다."가 표시되길 원한다. 그래야 왜 안 됐는지 안다.
38. 글쓴이로서, 삭제에 성공하면 그 글이 목록에서 바로 사라지길 원한다. 그래야 성공했음을 알 수 있다.
39. 글쓴이로서, 삭제 폼을 취소하고 닫을 수 있길 원한다. 그래야 마음이 바뀌었을 때 글이 남아 있다.
40. 방문자로서, 남의 글 비밀번호를 모르면 그 글을 삭제할 수 없길 원한다. 그래야 내 글도 남에게 지워지지 않는다.
41. 글쓴이로서, 삭제하려는 글이 이미 삭제됐다면 그 사실을 안내받고 싶다. 그래야 상황을 이해할 수 있다.

### 공통 / 화면

42. 방문자로서, 헤더에서 방명록 제목과 `개발자: 김정효 (202204195)`를 항상 보고 싶다. 그래야 누가 만든 방명록인지 안다.
43. 방문자로서, 제출 중에는 버튼이 비활성화되길 원한다. 그래야 두 번 눌러 중복 처리가 일어나지 않는다.
44. 방문자로서, 휴대폰 화면에서도 목록과 폼을 불편 없이 쓰고 싶다. 그래야 어디서든 방명록을 쓸 수 있다.
45. 방문자로서, 성공 여부를 알리는 별도 팝업 없이 화면 변화만으로 결과를 알 수 있길 원한다. 그래야 흐름이 끊기지 않는다.
46. 개발자로서, 비밀번호 확인이 반드시 서버에서 이루어지길 원한다. 그래야 브라우저를 조작해 권한을 우회할 수 없다.

## Implementation Decisions

- **기술 스택**: Next.js 16 App Router + TypeScript, Neon Postgres(`@neondatabase/serverless`, 이미 설치됨, `DATABASE_URL` 환경변수 사용), Vercel 배포. 코드 작성 전 `node_modules/next/dist/docs/`의 관련 가이드를 확인한다 (AGENTS.md 지침: 이 Next 버전은 학습 데이터와 다를 수 있음).
- **방명록 모듈 (핵심, 깊은 모듈)**: 모든 도메인 규칙을 담는 단일 모듈. 공개 인터페이스는 네 함수뿐이다.
  - `createEntry({ authorName, message, password })` → 성공(생성된 Entry) | 입력 오류(필드별 사유)
  - `listEntries()` → Entry 목록 (작성 시각 내림차순, 비밀번호 해시 제외)
  - `editEntry({ id, message, password })` → 성공(수정된 Entry) | 비밀번호 불일치 | 입력 오류 | 없는 글
  - `deleteEntry({ id, password })` → 성공 | 비밀번호 불일치 | 없는 글
  - 실패는 예외가 아니라 구분 가능한 결과 값(판별 유니온)으로 돌려준다. UI가 사유별 안내 문구를 고를 수 있어야 하기 때문이다.
  - 입력 검증, 공백 제거, 비밀번호 해싱·비교, 정렬, "수정됨" 판정이 모두 이 모듈 안에 있다.
- **저장소 인터페이스 (주입)**: 방명록 모듈은 저장소 인터페이스를 주입받는다. 운영용 구현은 Neon Postgres, 테스트용 구현은 메모리 저장소. 저장소는 저장·조회만 하고 규칙은 모르는 얇은 층이다. 비밀번호 해시는 저장소와 모듈 내부에만 존재하며 공개 Entry 타입에는 없다.
- **공개 Entry 형태**: `id`, `authorName`, `message`, `createdAt`, `edited`(수정 여부). 비밀번호·해시는 절대 포함하지 않는다.
- **스키마**: `entries` 테이블 하나.
  - `id` UUID 기본키 (DB에서 생성)
  - `author_name` text, not null
  - `message` text, not null
  - `password_hash` text, not null
  - `created_at` timestamptz, not null, 기본값 현재 시각
  - `updated_at` timestamptz, null 허용 (수정된 적 있으면 값이 있음 → "(수정됨)")
  - `created_at` 내림차순 정렬을 위한 인덱스
  - 스키마는 저장소에 보관된 SQL로 정의하고, Neon에 한 번 적용하는 방법을 README 또는 스크립트로 남긴다.
- **비밀번호 해싱**: Node 내장 `node:crypto`의 `scrypt` + 글마다 랜덤 salt. salt와 해시를 함께 한 문자열로 저장. 비교는 타이밍 안전 비교(`timingSafeEqual`). 추가 의존성 없음. 평문 비밀번호는 저장·로그·응답 어디에도 남지 않는다.
- **입력 규칙** (앞뒤 공백 제거 후 적용, 작성·수정 공통):
  - 작성자 이름: 1~20자
  - 메시지: 1~500자
  - 비밀번호: 4~20자. 단, 비밀번호는 공백을 제거하지 않고 입력한 그대로 저장·비교한다 (길이만 검사).
- **"없는 글" 처리**: 수정·삭제 대상 id가 없으면 "없는 글" 결과. UI는 "이미 삭제되었거나 존재하지 않는 글입니다." 안내.
- **Server Actions**: 작성·수정·삭제는 Server Actions로 처리한다. 액션은 폼 데이터를 꺼내 방명록 모듈을 호출하고, 결과를 폼 상태로 돌려주며, 성공 시 목록이 다시 그려지도록 캐시를 무효화하는 얇은 층이다. 권한 판단은 액션이 아니라 모듈에서 한다.
- **페이지 구성**: 단일 페이지. 헤더(제목 "미니 방명록" + `개발자: 김정효 (202204195)`) → 작성 폼 → 글 목록. 목록은 서버에서 `listEntries()`로 렌더링.
- **글 항목 UI**: 각 글에 [수정]/[삭제] 버튼. 누르면 그 글 아래 인라인 폼이 열림 (한 글에 한 폼). 수정 폼 = 현재 메시지가 채워진 편집창 + 비밀번호 + 저장/취소. 삭제 폼 = 비밀번호 + 삭제/취소. 비밀번호 불일치 시 폼 안에 빨간 글씨 "비밀번호가 일치하지 않습니다.", 입력값 유지. 성공 시 폼 닫힘.
- **시각 표시**: 한국 시간(Asia/Seoul) `YYYY-MM-DD HH:mm`. 서버/클라이언트 시간대 차이로 값이 달라지지 않도록 시간대를 명시해 포맷한다.
- **메시지 표시**: 텍스트로만 렌더링(React 기본 이스케이프), 줄바꿈 유지.
- **정리 작업**: `package.json`의 `name`을 `voting-app`에서 `guestbook-app`으로 변경. 기본 create-next-app 화면과 불필요한 에셋 제거.

## Testing Decisions

- **테스트 경계는 하나: 방명록 모듈의 네 공개 함수.** 테스트는 메모리 저장소를 주입한 방명록 모듈만 호출하고, 결과 값과 이후 `listEntries()`가 돌려주는 내용으로만 검증한다.
- **좋은 테스트의 기준**: 외부에서 관찰 가능한 동작만 검증한다 (예: "틀린 비밀번호로 수정하면 비밀번호 불일치가 반환되고 목록의 메시지는 그대로다"). 해시 형식, 저장소 내부 구조, 내부 헬퍼 함수 등 구현 세부는 검증하지 않는다. 구현을 리팩터링해도 동작이 같으면 테스트는 그대로 통과해야 한다.
- **검증할 동작 예시**:
  - 작성 후 목록에 나타나고, 목록이 작성 시각 최신순이다
  - 목록 결과 어디에도 비밀번호·해시가 없다
  - 각 필드의 빈 값·공백만·길이 초과가 입력 오류로 거부된다 (경계값 포함: 20자/21자, 500자/501자, 4자/3자)
  - 맞는 비밀번호로 수정하면 메시지가 바뀌고 `edited`가 참이 되며, 작성 시각과 목록 순서는 그대로다
  - 틀린 비밀번호로 수정·삭제하면 비밀번호 불일치가 반환되고 데이터가 바뀌지 않는다
  - 같은 이름의 두 글이 있어도 한 글의 비밀번호로 다른 글을 수정·삭제할 수 없다
  - 없는 id로 수정·삭제하면 "없는 글"이 반환된다
  - 맞는 비밀번호로 삭제하면 목록에서 사라진다
- **테스트 도구**: Vitest를 새로 추가하고 `test` 스크립트를 등록한다.
- **자동 테스트하지 않는 것**: UI 컴포넌트, Server Actions, Neon 저장소 구현은 얇은 층이므로 로컬 실행(`next dev`)과 Vercel 배포 후 수동으로 확인한다.
- **기존 사례**: 코드베이스에 기존 테스트가 없다. 이 모듈의 테스트가 첫 사례가 된다.

## Out of Scope

- 회원가입, 로그인, 계정 (ADR-0001)
- 작성자 이름 수정 (메시지만 수정 가능)
- 비밀번호 무차별 대입 제한(rate limiting)
- 관리자 삭제/관리 화면
- 비밀번호 찾기/재설정
- 스팸 방지(캡차 등)
- 페이지네이션, 검색, 필터
- 알림 팝업(토스트) 등 별도 성공 피드백
- UI·E2E 자동 테스트
